# Corvus text API v1 (offline candidate)

API-1 implements a **minimal OpenAI Chat Completions subset**, not full OpenAI
compatibility. No service is deployed or enabled by this change. Python 3.12 and the pinned
existing host dependency versions in deploy/lab/api-v1/requirements.txt are the
offline validation environment. Entry point:
`app.openai_api:app`; factory `create_app()` provides isolated test seams.

Client settings: Base URL `http://127.0.0.1:PORT/v1`, API key, model `corvus`.
The port must be selected/approved during a later Lab rollout; existing ports
and services are unchanged. There is no FoxWords or other application dependency.

## Contract

Both routes require `Authorization: Bearer KEY`:

- `GET /v1/models`: model list with public alias `corvus`; no filesystem/model
  paths, slot information, private sessions or upstream administration routes.
- `POST /v1/chat/completions`: `model` and `messages` required. Returns genuine
  upstream `id`, `created`, `model`, assistant content, `finish_reason`, and
  `usage.prompt_tokens/completion_tokens/total_tokens`. Whitespace is preserved;
  invalid/missing/inconsistent upstream envelopes fail safely, without fake usage.

Supported request fields:

| Field | Supported values / limits |
| --- | --- |
| model | `corvus` |
| messages | 1–64 messages; string content, nonempty; roles below |
| stream | omitted or boolean `false` |
| n | integer `1` |
| temperature | finite number 0–2, default 0.7 |
| top_p | finite number >0 and <=1, default 1 |
| max_tokens | integer 1–1024, default 512 |
| max_completion_tokens | exclusive alias for max_tokens; supplying both is an error |
| stop | one nonempty string or 1–4 strings, each <=128 characters |
| response_format | `{"type":"text"}` (default) or `{"type":"json_object"}` |

An optional leading sequence of system/developer messages is combined in order
into one system message, separated by two newlines. This model-template
normalization treats developer instructions as caller-owned system instructions;
it is not a general implementation of OpenAI instruction precedence. The
remaining messages must alternate user/assistant, beginning and ending with user.
Assistant prefill, mid-conversation system/developer messages, content arrays,
tools, files, image/audio input, arbitrary backend options, Thinking overrides,
unknown fields and query parameters are rejected explicitly. No values are
silently dropped from the accepted client contract.

Each JSON object answer is parsed and checked as a complete top-level object,
rejecting duplicates, non-finite numbers, invalid JSON and arrays. Original text
is returned unchanged. A valid object with finish_reason `length` remains marked
`length`; a truncated/invalid object produces 502 `invalid_json_output`, not a
false schema-success response. There is **no strict JSON Schema guarantee**.
Plain text can return empty content when the upstream reports `length` or
`content_filter`; no automatic retry or substitution of hidden reasoning occurs.

Request body: <=128 KiB including chunked bodies, uncompressed JSON; body deadline
5 seconds. Model-rendered input <=4096 tokens, output <=1024; these fit beneath
this deployment's 8192 context with headroom. The counting POST receives exactly
the same template and Non-Thinking settings as the single generation POST.
API-2 subsequently accepted two sequential real loopback SDK requests (text and
JSON), authentication/rotation and cleanup. This is local acceptance, not remote
HTTPS or persistent deployment acceptance.

Responses/errors include `Cache-Control: no-store`. Errors have
`{"error":{"message":"safe description","type":"...","param":null,"code":"..."}}`.
Codes: 400 invalid/unsupported input or context limit; 401 invalid credentials
(with WWW-Authenticate); 404 unknown route/model; 408 body deadline; 413 body
size; 415 media/encoding; 429 busy/rate limit (Retry-After: 10 for busy, remaining window for rate limit); 499 disconnected
client when still observable; 500 internal error; 502 invalid/upstream response;
503 disabled/unavailable/config failure; 504 response deadline. Provider bodies,
request values, tracebacks, keys and internal exception messages are not returned.

## Authentication, provisioning and revocation

The exported app is disabled by default. Independent future settings are in
`deploy/lab/api-v1/config.env.example`; that sample is not loaded automatically.
Never inherit a full Lab environment or reuse WebUI, STT, FoxGate or model keys.

Keys must contain 43–128 ASCII URL-safe characters; generate at least **32 random
bytes** (`secrets.token_urlsafe(32)`). Only SHA-256 digests are stored on the
server, one lowercase 64-character hex digest per line (1–16 unique entries,
<=2048 bytes). No labels, blank lines, JSON or comments are accepted. File must
be regular, singly linked, owned by service EUID, mode 0600; immediate parent
must be owned by service EUID and mode 0700. Final directory/file symlinks and
special files are rejected. Open uses a checked directory FD and O_NOFOLLOW;
metadata drift fails closed. All ancestors must also be trusted/protected from
other writers; the checker is not a substitute for safe operator provisioning.

Read/validate afresh on every request; comparisons use constant-time digests and
check every entry. Missing/malformed configuration returns 503 rather than using
a stale cached allowlist. Wrong/missing/malformed/duplicate Bearer headers return
401 before body buffering. Keys in query strings are not supported.

Future operator procedure, **not performed by API-1**:

1. Create a persistent private directory owned by the intended service account,
   mode 0700, outside Git and outside private conversation storage.
2. Generate a key into a new exclusive mode-0600 private client file; never pass
   it as a CLI argument, save it in shell history, or print it to a shared log.
   Provision its SHA-256 hex digest in a new mode-0600 file in the same server
   directory. Review ownership/modes, then atomically replace the configured digest
   file using `os.replace` on the same filesystem. Do not edit the active file
   in place. The service only needs read access to that directory/file.
3. To rotate, atomically install old+new digests, migrate clients, then atomically
   install only the new digest. To revoke one key, omit only its digest. Changes
   affect the next authentication check without restarting any shared service.
   An already-authorized request may finish; revocation does not cancel inference.
4. An empty/removed file disables authentication (503). Keep required digest
   configuration backups private and preserve metadata. No key-management server,
   account database, billing, scopes or management endpoints are introduced.

A minimal **fresh provisioning illustration** (replace both paths, do not run
against existing material) writes the raw key only to the client location:

```python
import hashlib, os, secrets
from pathlib import Path

os.umask(0o077)
client_path = Path("/PRIVATE/CLIENT/new-key")
server_dir = Path("/PRIVATE/CORVUS_API")  # pre-provisioned trusted 0700 directory
key = secrets.token_urlsafe(32)
with client_path.open("x") as f:
    f.write(key + "\n")
with (server_dir / "keys.sha256.new").open("x") as f:
    f.write(hashlib.sha256(key.encode("ascii")).hexdigest() + "\n")
# Initial install only; preserve/review any existing keyset before rotation.
if (server_dir / "keys.sha256").exists():
    raise RuntimeError("Existing keyset: review rotation instead of overwriting")
os.replace(server_dir / "keys.sha256.new", server_dir / "keys.sha256")
```

Restrict the future service to the digest file; keep the raw client key outside
its accessible paths. Rotation follows the explicit overlap/remove procedure
above, preserving all other authorized digests.

## Request example (after a separately approved activation)

A backend client can load its key without placing it in process arguments:

```python
from pathlib import Path
import httpx

base_url = "http://127.0.0.1:PORT/v1"  # replace PORT after operator approval
key = Path("/PRIVATE/CLIENT/key").read_text().strip()
with httpx.Client(timeout=100) as client:
    reply = client.post(
        base_url + "/chat/completions",
        headers={"Authorization": "Bearer " + key},
        json={"model": "corvus", "messages": [{"role": "user", "content": "Say hello."}],
              "stream": False, "max_tokens": 128},
    )
    reply.raise_for_status()
    print(reply.json()["choices"][0]["message"]["content"])
```

Standard non-streaming SDK calls can use the same three settings and supported
fields. This is a wire contract, not evidence that every SDK/app has been tested.
Do not place a private API key in browser JavaScript; use an application backend.

## Documentation, ownership and limits

`GET /openapi.json` is Bearer-protected and describes typed requests, responses,
errors and HTTPBearer security. Interactive `/docs` and `/redoc` are disabled to
avoid an unauthenticated/CDN-dependent UI; fetch the schema through an authenticated
client and inspect it locally. No public health/private conversation endpoints
are mounted. CORS is disabled by default; it is not an authentication boundary.

One API worker, one actual inference worker, no waiting queue; excess requests
return 429. A process-local rolling limit permits six generation attempts/minute,
including rejected bodies. Run exactly one ASGI worker/instance for that local
limit; multiple processes would each have their own allowance. This does not
reserve or preempt the shared Qwen slot. API response deadline is 90 seconds,
including body/model counting and queue waits. Timeout/disconnect/task cancellation
never causes a resend and never releases a still-running **real concurrent
future**. A cancelled asyncio wrapper is not proof its thread has settled.

Reuse the existing foreground tracker with unique logical name `api`; optional
`CORVUS_API_FOREGROUND_REGISTRY_DIR` allows approved shared-registry publication.
Do not use logical name lab/production or add api as a required Hindsight peer.
Existing readers count any valid live api publisher as busy; missing optional api
is not an outage. No scheduler, Retain Ledger or Hindsight logic changes occur.

The socket transport remains synchronous and finite. A socket read begun before
the deadline can finish after the client receives 504; the API keeps its slot and
foreground ownership until the worker settles. Outer HTTP timeout/close does not
prove remote inference stopped. Shared services may still wait. This is bounded
resource ownership, not a global cancellation/latency guarantee.

Transport is opt-in in model_client, fixed to the configured literal loopback
HTTP model target, with proxies/redirects disabled and response reads bounded to
256 KiB. The legacy generate_chat_completion/count_input_tokens functions are
unchanged. No automatic retries occur, including after unknown outcomes.

## Isolation, future rollout and rollback

The API imports no conversation/personality/memory modules, performs no canonical
startup or dense recovery, and mounts no /api routes. Caller messages are the only
context: no default companion prompt, retrieval, Evidence Log, database writes
or Hindsight retention. Full companion functionality stays on existing routes.
The existing BackgroundTasks -> durable retain-intent/automatic recovery gap is
unchanged and is not certified by API-1. Statelessness does not imply secure
GPU-buffer erasure or zero retention in existing upstream process logs/memory.

Remote HTTPS ingress is **not available**. Existing FoxGate requires browser
Cookies. A later narrow API-only TLS route must be separately reviewed; do not
bypass its whole realm or expose llama.cpp directly. Do not change current Lab,
Production/Demo, model, STT/TTS, FoxGate or Hindsight configurations to try this.

Before later activation, use an isolated loopback service account/sandbox denying
all private/Lab/Demo databases and conversation storage. Allow only the API key
file, readonly source/dependencies and (if approved) foreground registry metadata.
Use one worker and `--no-access-log` (URLs can contain mistakenly supplied keys);
keep debugging/request-body tracing disabled. Verify actual caller fields and
JSON with synthetic inference only under separate authorization. Rollback is
stop/disable only the new API process/route; revoke its keys. No Corvus memory
rollback or shared-service restart should be needed.
