## 0. 真实数据对原假设的修正

1. **检索可靠性比相关性更靠前。** 在 `b796650` 上对 8 个日常问题做真实检索（不调模型），有 4 个是 `PROVIDER_FAILED`（Node.js 最新 LTS、最新 macOS、硬件问题，以及一次 uv 和 pip）。原因：
   - 路由把“最新”“刚才”当成新闻词，查询变成“新闻类 + 只搜过去一天”。版本类问题因此搜不到结果（DDGS 返回 “No results found”）。重新核实类的问题（“你**刚才**的说法”）也是同一个原因。
   - MVP 把搜索计划截断为只执行第一次尝试（`single_attempt`），计划里已有的后备尝试从来没有执行过。
   - DDGS 本身偶发返回空结果（同一个查询，一分钟前成功，之后失败）。
2. **O1R 的目录页包含查询的全部锚点**（`python`、`3.13`），所以只看锚点覆盖拦不住它。真正的区别在于这个页面能提供的证据太少：一共只有 244 个字符，且大部分是导航文字。
3. **耗时实测**（`b796650`，真实网络）：
   - 一次搜索 1.8–12 秒；
   - 每次抓取 1.2–5.3 秒；
   - 提取不到 0.5 秒；
   - 生成在 W1.1 验收中是 1–25 秒，**并且会和 Hindsight 的后台抽取争抢同一个 llama**。

## 1. 实施项与提交顺序

### W2-a 可观测性（先做；只记录，不改变行为）

- `prepare_web_mvp` 记录：
  - `search_ms[]`（每次尝试一项）、`fetch_ms[]`、`extract_ms[]`；
  - `retrieval_ms`（检索阶段总计）；
  - `evidence_ms` = `retrieval_ms` 减去前三项之和（包括分段、排序、选证据和来源接受）。
- `model_client` 在线程本地保存 llama.cpp 返回的 `timings`。runtime 据此记录：
  - `generation_ms`：墙钟时间；
  - `model_compute_ms`：`prompt_ms + predicted_ms`；
  - `model_wait_ms`：前两项之差，即排队、共享 GPU、HTTP 的开销；
  - `prompt_tokens`、`completion_tokens`。
- 另外记录 `context_ms`（包括召回）和 `turn_ms`。结果放在 `result["web_timings_ms"]`，并加入 API 白名单。不写入持久化数据，不打日志正文。
- 判断规则：只有当测得的抓取阶段中位数大于 5 秒，**并且**它占整轮耗时的比例最大时，才考虑并行抓取。本阶段不实施并行。

### W2-r 检索可靠性（数据驱动新增，改动很小）

- **路由**：查询中含版本或发布类词（`版本|正式版|LTS|release|version|发布|更新日志|changelog|新特性|新功能`）时，不再判为新闻意图，改走普通搜索，不加时间范围。
- **每个计划的最后**追加一次宽泛的后备尝试：普通类别、同一语言、不加 bang、不限时间；如果与已有尝试完全相同则不加。
- MVP 执行**完整计划**（去掉 `single_attempt` 截断）。前一次尝试失败或为空时才执行下一次，所以只在失败时增加耗时。尝试次数最多 3 次。
- **查询清理**：去掉开头的请求类用语，例如“请联网核实”“帮我查一下”“你刚才（关于）…的说法”。如果清理后少于 4 个字符，就保留原文。
  - 只说“核实你刚才说的”、完全没有主题的情况，需要借助会话上下文改写查询，**不在 W2 范围内**。

### W2-b 证据相关性（核心）

在收集器里增加一个可选的 `candidate_relevance` 钩子。**只有无显式要求的路径会使用它**，显式要求路径保持不变。判断全部基于现有 ranker 的输出：选中证据所对应排序段落的 `matched_terms` 和 `exact_phrase_match`。

一个候选页面需要**同时满足**：

1. **锚点覆盖**：查询中的锚点（来自 `lexical_terms` 的 ASCII 或数字项，去掉 `what`、`new`、`latest` 等通用英文词）必须都出现在被选段落的 `matched_terms` 里。锚点有 3 个及以上时，允许缺 1 个。
2. **纯中文查询**（没有锚点）：被选段落需命中至少 2 个不同的中文 bigram，或有一段 `exact_phrase_match`。
3. **证据量**：被选证据合计至少 `MIN_EVIDENCE_CHARS = 400` 个字符。目录页、导航页、只剩标题的页面会因此被拒绝。

不满足条件时，在 `missing` 中记为 `relevance` 或 `thin_evidence`，然后尝试下一个候选。全部不满足时，走现有的“只给链接”降级，**不调用模型**。

**这不是语义验证**：一个内容足够长、关键词也对得上、但实际答非所问的页面，仍然可能通过。

### W2-c 多来源与预算

- 无显式要求时，以 `min_sources=2` 收集：优先找到两个不同的合格来源，候选上限仍是 3 个。
- 只有一个合格来源时，正常作答，`missing` 中记录 `single_source`。**这个来源按完整的 3,600 字符预算重新选证据**（复用现有的 build/rank/select），而不是只用 1,800 字符。
- 有两个来源时，每个来源 1,800 字符，总预算不变。
- `[web_n]` 的编号、`source_map`、Plan C 的来源边界和 E2 都不变。

### 顺带修复（成本很小）

- E2 在表格行中间标注时多加了一个 `|`，导致表格多出一列。改为：句子片段不以 `|` 结尾时，不再补 `|`。

### 不在 W2 范围内

- 并行抓取：等 W2-a 的数据出来再决定。
- 基于会话的查询改写（无主题的“核实你刚才说的”）。
- 搜索服务换成 SearXNG，或增加多个 Provider。
- 共享 Qwen 的排队问题：W2-a 只做测量，缓解放到 Streaming / Voice 阶段。
- 非联网聊天中的记忆污染（M1）。
- 语义级的事实验证。
