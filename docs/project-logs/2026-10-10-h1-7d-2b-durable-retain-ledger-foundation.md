## Ledger/file design and scope

`app/retain_ledger.py::RetainLedger` takes an explicit path. The intended future
location is the existing private `h1-shadow-recall.jsonl` under the Lab data root.
Construction has no I/O and there is no live default instance. No existing file
or record is migrated or rewritten.

`app/durable_jsonl.py` extracts the proven append/flock/fsync machinery from
`app/hindsight_shadow.py::append_observation`. The shadow writer keeps its Lab-only
guard and existing serialization/append behavior and delegates to the shared
helper. Ledger appends additionally validate the existing history plus proposed
event under the same exclusive file lock.

**No live retain path uses the ledger yet.** `retain_completed_turn` still sends
`async:false` with zero retries. No intents are generated by `post_chat`, and no
reconciliation hook, Hindsight call, runtime configuration or deployment is added.
Lab/Production services, Hindsight, model endpoints and foreground registry are
not changed or restarted.

## Event schema and operation identity

Every new event has `record_type:retain_ledger`, `ledger_version:1`, `event_type`,
canonical UUID `operation_id`, and timezone-aware UTC `recorded_at`.

The four event types are:

- `RETAIN_INTENT`: user/assistant message IDs, session, bank, deterministic
  document ID, contract version and payload fingerprint.
- `RETAIN_SUBMISSION_ACCEPTED`: records validated submission acceptance later.
- `RETAIN_SUBMISSION_AMBIGUOUS`: optional error describing an uncertain result.
- `RETAIN_STATUS`: actual Hindsight status, optional next retry timestamp, retry
  count and error. This also represents terminal observations; a separate
  terminal event is unnecessary.

`record_intent` accepts a caller-supplied UUID or generates UUID4 before appending.
It returns the recoverable intent only after durability succeeds. A duplicate
intent with the same UUID/material is permitted; conflicting intent material is
rejected under the append lock. Outcome events require a preceding intent.
Different UUIDs remain independent operations; document identity does not merge
them. Later event recording always uses the original operation UUID.

Document identity is validated as
`corvus-lab:turn:{user_message_id}:{assistant_message_id}`, with positive ordered
message IDs. This foundation targets the current Lab retain contract and does
not add Production retain publication.

## Payload fingerprint contract

The fingerprint is SHA-256 over UTF-8 canonical JSON containing:

- Hindsight bank.
- Contract version.
- The exact single-item request material: `async:true` and `items:[item]`.

Serialization sorts object keys, uses compact separators, preserves Unicode,
rejects non-JSON/non-finite values and requires string object keys. All item
fields participate, including document ID, content, metadata, context, timestamp
and any other supplied item fields. Omitted fields and explicit nulls remain
distinct. Retain timestamps are payload material; ledger timestamps, HTTP timing
and operation UUID are excluded. Thus identical payloads have identical hashes
regardless of event time/key ordering, while material changes alter the hash.

The ledger stores the fingerprint and canonical source linkage, not another copy
of conversation content. Future submission/reconstruction must check the exact
payload against the recorded contract/fingerprint before replay.

## Durability and crash behavior

The shared writer uses `O_APPEND`, `O_CLOEXEC`, `O_NOFOLLOW`, regular-file checks,
mode `0600`, and exclusive `flock`. It completes partial writes, fsyncs the file
and parent directory, and only then reports success. A caught write/fsync failure
attempts rollback to the original size while holding the lock and is surfaced to
the caller. Rollback failure is also never reported as success.

An actual process crash may leave a partial tail, because it cannot execute
rollback. A record is accepted only when the entire JSON object and terminating
newline are present. A subsequent append refuses an incomplete tail. No crash
repair, truncation of historical records or automatic migration is implemented.

Ledger validation under the writer lock prevents a race between checking UUID
identity/state and appending an event. Readers use a shared lock to obtain a
consistent snapshot and do not write or repair the file. Reading a missing file
returns an empty mapping without creating it.

## Reconstruction and fail-safe rules

`reduce_events` is pure and returns one `RetainState` per operation UUID. It
tolerates existing comparison records without `record_type` and existing
`retain_outcome` records, preserving them on disk. Legacy OK outcomes are not
interpreted as completion of a new ledger operation.

Reconstructed state includes the intent, submission state, last observed
Hindsight status, terminal status, retry information, error and update timestamp:

- Intent-only state is `NOT_ATTEMPTED` and unresolved. This means no submission
  result is recorded, **not proof that a POST never physically ran**; future
  reconciliation must still reuse the same UUID after an acknowledgment gap.
- Acceptance remains unresolved until terminal status is observed. Later
  ambiguous replay cannot downgrade known acceptance.
- Ambiguous submission, pending and processing remain unresolved. A non-missing
  status observation can establish acceptance without a recorded HTTP ACK.
- Completed is terminal completed. Failed/cancelled are terminal failures;
  observing a later retry as pending/processing makes failed/cancelled work
  unresolved again.
- `not_found` does not imply acceptance or erase recorded terminal completion.
  Contradictory running/failure status after completed is rejected rather than
  silently downgrading completion.

Malformed JSON, missing new-event fields, duplicate JSON keys, unknown
version/event/type, orphan outcomes, conflicting UUID material and incomplete
tails raise an error. No trusted partial reduction is returned, so damaged tail
records cannot fabricate COMPLETED state. Damaged history blocks further ledger
publication and requires explicit repair outside this foundation.

Reads and ledger append validation currently scan the complete file. This is a
small correctness primitive; bounded reconciliation/lifecycle work is not yet
implemented. No queue/workflow framework or canonical SQLite schema is added.
